## 4. 暂停、续播与打断（阶段 3，建议戴耳机）

推荐顺序：先在「正常停顿」用耳机测，再换「慢速表达」；外放场景单独记录。所有时刻用 `window.__realtime.state.metrics` 核对最近 100 条 `suspected`、`pause`、`dismissed`、`resume`、`confirmed`、`endpoint` 事件，毫秒值来自浏览器单调时钟。

- [ ] AI 正在播放时开口说一句话：状态先显示「听到你的声音，正在确认…」，播放**暂停**但不立即取消
- [ ] 持续说话约 350 ms 后确认打断：状态为「正在打断，请继续说…」，播放停止，后台该轮取消（`error_code=interrupted`），不继续合成后续句子
- [ ] 说话结束后自动识别并提交新一轮，中途出现「等待模型释放…」属正常
- [ ] 打断后能立刻继续对话，不被「请先重试上一条」挡住
- [ ] 被打断那一轮仍出现在历史里并标注中断，但**不**作为下一轮上下文（观察回复是否接错话题）
- [ ] 播放时只咳嗽/敲桌/短噪声：先暂停，结束后从暂停位置恢复，无重复或跳句
- [ ] 播放时说「嗯」「对」等短促附和且不继续：应恢复播放；若被确认为打断，记录为已知限制（中文语义模型未启用）
- [ ] 播放时说话后又停住、始终没有持续人声：约 2 秒无法裁决时转为确认打断，不长时间卡住
- [ ] 播放时按「停止播放」：立即停播，不取消已完成的回复；随后可继续监听
- [ ] 暂停期间网络流结束：恢复后仍播完缓冲才上报本轮结束，不提前切走
- [ ] 播放时短于 150 ms 的声音只参与插话判断，不成为用户消息；普通提问仍按 500 ms 最短录音
- [ ] 结束对话或切换声音时若有回复在途：模型释放（`/api/health` 的 `busy` 变 false），麦克风关闭、播放停止，旧恢复/播放回调失效
- [ ] 正常聊天页（非实时页）的取消行为保持原样（终态为 `text_failed`/`audio_failed`，不变成 `interrupted`）
- [ ] 不说话、只是播放：不应自触发打断（回声消除生效）；外放时误触发次数：____ / 10 分钟（耳机应为 0）

每个场景至少 30 次，冷启动与预热分开，固定硬件、声音、LLM、麦克风和耳机状态，记录原始值、中位数、P95 和最大值：

| 指标 | 记录项 | 首轮门槛 |
| --- | --- | --- |
| 打断响应 | 有效起声至本地暂停，`pause.response_ms` | 预热后 P95 ≤ 300 ms |
| 误打断恢复 | 判定噪声/附和至原播放恢复，`resume.response_ms`；恢复后无重复/跳句 | P95 ≤ 300 ms |
| 接话延迟 | 用户说完至浏览器实际出声；与同机旧实现对比 | P95 增幅 ≤ 200 ms |
| 噪声误打断 | 固定噪声与外放场景中导致实际取消的误判次数 | 相同样本下较旧实现减少至少一半 |

实测：pause P95 ____ ms；resume P95 ____ ms；接话 P95 ____ ms（旧实现 ____ ms）；误取消 ____ 次 / ____ 次样本；缓冲耗尽 ____ 次 / 10 轮。

语义阶段待办：当前只有能量与持续时间启发式，**未启用中文语义轮次模型**。按方案准备 ≥30 段带标签的中文录音（句内停顿、附和、真实插话），逐条记录混淆矩阵、每段结果、模型资源占用和新增延迟，再决定是否启用。未通过前不要宣称能可靠区分「停」与「嗯」；急需停播时用「停止播放」。

## 7. 性能测量（按方案要求记录）

先停应用（避免两个进程抢 GPU），再跑内置基准（本地真实引擎、不调用聊天服务）：

```sh
# 默认模式（cached）
.venv/bin/python benchmark_voice.py --voice <声音UUID> --runs 6

# 对照：整帧编译
.venv/bin/python benchmark_voice.py --voice <声音UUID> --runs 6 --depth-mode compiled --verify

# 对照：块大小（影响首块延迟）
.venv/bin/python benchmark_voice.py --voice <声音UUID> --runs 3 --chunk-frames 8
```

- [ ] 生成的 `web-test-artifacts/benchmark-*/benchmark.md` 中，短句与中句各至少 5 次热态；首个短句作为冷启动单独记录
- [ ] 核对表内三列：RTF 原始值、中位数、最大值；首块中位数
- [ ] **对比两种深度模式**：`cached` 与 `compiled` 各跑一遍，确认中位数差异是否在噪声内（本机约 2–4%），并检查 `--verify` 是否通过
- [ ] **对比块大小**：4 帧与 8 帧各跑一遍，确认首块延迟与 RTF 的取舍（本机 4 帧首块约 455 ms，8 帧约 700 ms）
- [ ] 抽查其中 1–2 个 WAV 能正常播放且非静音（证明测的是有效合成，不是快但坏）
- [ ] 端到端首音仍需浏览器实测（说话结束 → 实际听到第一声），不要用服务端 `first_audio_ms` 代替
- [ ] 实时页跑 10 轮，记录缓冲耗尽/停顿次数：____（本机中位 RTF < 1，理论上不应耗尽；若仍耗尽，先确认没有并发 GPU 任务）
- [ ] 结论判定：热态 `rtf < 1` 才谈得上持续播放；本机训练后声音中位 0.92–0.97，但短句最大 1.158、实测单条 1.006，属**接近实时、不承诺严格实时**

本机参考值（M1 Pro / 16 GiB，2026-11-17，安静环境，`cached` + 4 帧）：基座 0.875 / 0.826（首块 451/456 ms）；训练后 adapter 0.966 / 0.915；`compiled` 0.860 / 0.795；`native` 对照 2.265 / 2.222（说明优化本身约 2.6 倍收益）。用你自己的素材复测后以新数字为准；**测量时不要并行跑训练**，否则数字会明显偏高。
